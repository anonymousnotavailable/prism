# Prism Audit — 2026-08-07

First run of the `.prism/` autonomous-improvement routine's memory system on
this repo. Prism is already a mature Streamlit app (v5+, per git history) —
Auto Cleaner, Hell Mode, India Mode, Atlas (JARVIS-style voice copilot with
an intent router), Auto Analyst (agentic "Run Full Analysis"), Anomaly
Detection, Stats Lab, ML Lab, SQL Lab (DuckDB workbench), Forecasting,
Clustering, Drift, SHAP explainability, a corpus benchmark harness, and a
FastAPI layer (`api/main.py`) exposing core analysis as tools. No React/
Next.js shell exists yet — the whole product is the Streamlit app; the
routine brief's "React/Next.js glassmorphic PWA shell" describes a future
state, not the current repo (noted for accuracy, not actioned this run —
no architecture rewrites per the guardrails).

## Findings this run

### 1. [FIXED] Atlas side panel eats the entire screen on phone/PWA widths
`modules/theme.py`'s `.st-key-atlas_side_panel` rule is `position: fixed;
width: 328px; right: 0` with **no responsive override at all**. On any
viewport under ~400px (i.e. every phone), that fixed panel covers nearly
the whole screen, burying every tab underneath it. Directly contradicts the
"installable on phone" PWA pitch. Fixed with a `@media (max-width: 900px)`
rule that hides the panel below that width — Atlas is still fully reachable
through the always-visible `st.chat_input` command bar at the page bottom
(`app.py`'s `typed_command`), which is a separate element unaffected by
this change.

### 2. [LOGGED, NOT FIXED — HIGH PRIORITY for next run] Page-level auto-scroll-to-bottom hijack
Confirmed via live DOM inspection (Playwright + `evaluate`): the moment
`st.chat_input` is used anywhere on a page, Streamlit wraps the **entire**
main content area in `section[data-testid="stAppScrollToBottomContainer"]`
and force-scrolls that whole container to the bottom on load/rerun — not
just a chat pane, the *whole app*. Reproduced with `scrollTop` snapping to
`scrollHeight - clientHeight` (e.g. 14,580 of 15,424px) on a fresh page
load + file upload, no user interaction. On a short mobile viewport this
means the page opens already scrolled almost entirely past all real
content — Overview, nav, everything — landing near the chat input.

Two mitigations attempted this run, both failed or were inconclusive:
- **Un-fixing the Atlas panel into normal flow** (so it wouldn't need its
  own fixed overlay) made this *worse*: the panel's own message list used
  to scroll independently inside its `overflow-y: auto`; once it joined
  normal flow, the top-level auto-scroll-to-bottom pulled the *page* down
  past it too. Reverted in favor of `display: none` (finding #1).
- **A `components.html()` JS guard** (`window.parent.document` reach-through,
  same technique as `modules/ui.py`'s existing `render_tab_jump_script`)
  that remembered `scrollTop` across reruns via `window.parent` and
  restored it when Streamlit snapped to the exact bottom. Did not resolve
  it in testing — the correction window (8 animation frames) likely loses
  the race against Streamlit's own scroll assertion, which may re-run more
  than once per rerender. Reverted rather than ship an inert 40-line JS
  injection with no measurable effect.

Next-run starting point: investigate whether newer Streamlit versions
expose a way to opt a `stAppScrollToBottomContainer` out of the pin (a
config flag or an undocumented data attribute), or whether the JS guard
needs a persistent per-frame loop (not just 8 frames after mount) with a
real user-scroll listener (`wheel`/`touchmove`) to distinguish intentional
scrolling from the framework's own jump — that's a fair amount of extra
risk (fighting the framework every frame) and deserves a dedicated,
unhurried session rather than a slice of a feature-focused run.

### 3. [LOGGED, NOT DIAGNOSED — HIGH PRIORITY for next run] A narrow-column render at ~390px width
Independent of #1 and #2: at a 390px viewport, *some* element (confirmed via
`elementFromPoint` to contain real page text — the "Quick tour" onboarding
copy, the footer, and Atlas's own "heard: ..." acknowledgment all appeared
here at different times) renders wrapped one-or-two-characters-per-line in
a ~20-40px-wide strip pinned to the left edge, regardless of which tab is
active. A `stHorizontalBlock` (likely the `nav_col, more_col =
st.columns([5, 1.4])` split around the "Advanced Tools" popover) was
observed at `width: 16px, x: -236` (off-canvas) in the same session, which
may or may not be the same element — not conclusively tied together this
run given time spent on #2. Needs a focused DOM trace at exactly 390-414px
(iPhone-class widths) with the scroll bug (#2) neutralized first, since the
two compound and make it hard to isolate which element is which without
scrolling.

**Recommendation for next run**: dedicate the first block of a cycle
specifically to mobile-viewport layout (no new features that cycle), using
the diagnostic scripts and findings above as a starting point rather than
rediscovering them.
