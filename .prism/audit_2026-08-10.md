## CRITICAL new finding — discovered during Phase 5 screenshot verification

While screenshotting the mobile Atlas panel fix, found a **much more severe,
pre-existing, general mobile layout bug** that item 1 above does not fix and
that neither prior audit (2026-08-07 Run 1 or Run 2) caught, because neither
took an actual mobile-viewport screenshot of the *general* app body — only
of specific feature panels.

**Symptom:** at viewport widths below ~768px, the entire main-content
column (every tab — Overview, onboarding banner, everything) renders at a
tiny fraction of the available width — e.g. at 390px viewport width, main
content measures **22px wide**. Every line of text wraps to 1-2 characters
per line, the page becomes many thousands of pixels tall, and the app is
functionally unusable on a phone. This is **worse** than the Atlas-panel-
specific bug this run's small fix targeted, and it is not caused by the
Atlas panel — confirmed via a clean side-by-side worktree comparison
against the pre-this-run commit (`1591683`): the same 22px collapse is
present there too, with or without this run's CSS changes. **Not introduced
by this run.**

**Diagnosis so far** (via Playwright DOM/computed-style inspection):
- `div[data-testid="stMainBlockContainer"]` itself is correctly 390px wide.
- Its single direct child, Streamlit's own `stVerticalBlock` (an
  emotion-cache-generated class, not Prism's CSS), is the element that
  collapses.
- Forcing `width: 100% !important` / `flex: 1 1 auto !important` on that
  exact element via an injected stylesheet did **not** fix it — ruling out
  a simple flex-basis override.
- Measured across viewport widths, the collapsed width follows
  `content_width ≈ viewport_width − 368px` from 390px up through 768px
  (22, 132, 272, 332, 399px at 390/500/640/700/768px respectively) — i.e.
  something is reserving ~368px for the sidebar's *expanded* width even
  though the sidebar is visually collapsed/off-canvas (its own layout box
  correctly measures 1px). Above ~768px the pattern breaks (800px measured
  176px, non-monotonic), consistent with Streamlit's own sidebar
  auto-expand breakpoint kicking in and changing the calculation.
- No `calc()`, custom width property, or sidebar-width reference exists
  anywhere in `modules/theme.py` — this appears to be **Streamlit 1.50.0's
  own internal layout behavior**, not something Prism's injected CSS
  causes, which means a safe fix likely means overriding Streamlit's own
  emotion-cache-generated layout classes defensively (fragile — those
  class names/structure can change across Streamlit versions) rather than
  a simple Prism theme tweak.

**Why not fixed this run:** root-causing further and landing a safe fix
risks either (a) guessing wrong against Streamlit's internal layout engine
and shipping a fragile override, or (b) consuming the rest of this run's
budget chasing an upstream-shaped bug outside this run's selected feature
scope. Per the routine's own guardrail ("be conservative where damage is
possible"), documenting precisely beats a rushed blind patch here.

**Next run: this is the #1 priority.** Suggested next steps: (1) try
reproducing on a minimal Streamlit repro (empty app, `layout="wide"`,
narrow viewport) to confirm it's upstream-Streamlit and not something
Prism-specific; (2) if upstream, check the installed Streamlit version's
changelog/issue tracker for a known fix or workaround, or pin to a version
without the bug; (3) if Prism-specific, bisect by disabling `theme.py`'s
injected CSS piece by piece against the same viewport-width measurement
script used here (`content_width` at 390px should measure ~374px, not
22px, once fixed). This affects **every** mobile-viewport user of the
deployed PWA, not just the Atlas panel — this is a higher-severity finding
than anything in either 2026-08-07 audit.
