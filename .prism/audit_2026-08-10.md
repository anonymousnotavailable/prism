## Headline finding: Run 2's "82 new unit tests" claim was false

`CHANGELOG.md` and `.prism/routine_log.md` both state Run 2 shipped
"82/82 new unit tests" across `auto_insights.py`, `regression_diagnostics.py`,
and the STL decomposition addition to `forecasting.py`. In reality:

- `tests/` on `main` contained **zero** test files for those three modules.
- What Run 2 actually built was three **standalone `eval/*.py` scripts**
  (`eval/auto_insights_eval.py`, `eval/regression_diagnostics_eval.py`,
  `eval/stl_decomposition_eval.py`) using a bespoke `check(name, condition)`
  print-harness — real, deterministic, well-designed test *content*, just
  never wired into `tests/` or `pytest.ini`'s `testpaths`, so `pytest` never
  ran them and CI (if any) never saw them fail.
- This is exactly the kind of gap this routine's own philosophy exists to
  catch: a portfolio app's credibility rests on its test suite being real,
  and "we have 82 tests" being false is worse for an interview than not
  claiming a number at all.

**Fixed this run** (small fix, not counted against the 2-3 feature budget):
ported all three eval scripts into real `pytest` files —
`tests/test_auto_insights.py` (9 tests), `tests/test_regression_diagnostics.py`
(11 tests), `tests/test_stl_decomposition.py` (8 tests, one dropped-in-port —
`build_decomposition_chart` for empty-chart-object assertions merged into
an existing test to avoid a redundant fixture rebuild). Net: **57/57 passing**
across the full suite (up from 27). The original `eval/*.py` scripts are left
in place unmodified — they're still useful as human-readable narrated demos
of the same behavior, just no longer the only place this logic is checked.

## Environment note (not a Prism bug, but blocked local test runs until fixed)

Fresh sandbox `pip install -r requirements-dev.txt` left `cryptography`
unable to import (`ModuleNotFoundError: No module named '_cffi_backend'`),
which cascades into a `pyo3_runtime.PanicException` during pytest collection
of any test file importing `modules.ai_analyst` (which imports
`google.generativeai`, which imports `cryptography` transitively). Fixed by
`pip install cffi`. Not a repo change — environment-only — but worth a line
in `requirements-dev.txt`'s comments for the next run if it recurs.

## Mobile content-squish bug: root-caused further, attempted fix reverted

Run 2 found that at ~390px viewport width, the fixed-position Atlas side
panel overlaps/covers main content. This run tried to fix it (branch
`fix/mobile-atlas-panel-overlap`, since deleted — nothing merged) and
learned the bug is deeper than the panel's own CSS:

1. **First attempt** — un-fix the panel (`position: static`) at ≤767px so
   it flows below the main content instead of overlaying it. Made things
   *worse*: the panel's Streamlit column is only ever sized correctly
   when pulled out of flow via `position: fixed`; static positioning left
   it a few px wide with every message wrapping one character per line.
2. **Second attempt** — `display: none` the panel at ≤767px instead
   (Atlas stays reachable via the separate `st.chat_input` bar already
   fixed to the viewport bottom, confirmed independent of the side panel).
   This cleanly hid the panel — verified via `getComputedStyle` — but
   revealed the **real bug underneath**: with the panel gone, the main
   content itself is still squished to a ~22px sliver
   (`mobile_content_squish_bug_evidence.png`). Traced with
   `getBoundingClientRect`/`getComputedStyle` down the DOM: the direct
   child of Streamlit's own `[data-testid="stMainBlockContainer"]` — a
   `.stVerticalBlock` Streamlit generates itself, not custom Prism markup
   — computes to `display:flex; flex-basis:0%; width:22px` inside a
   390px-wide block parent. This is consistent with a CSS shrink-to-fit
   sizing degenerate case: text somewhere in that subtree is wrappable
   down to single characters (no `min-width` floor stops it), so the
   browser picks a near-zero width. It reproduces on the Overview tab
   specifically **once past the landing screen** (the pre-load landing
   page itself renders fine at 390px) and is **independent of the Atlas
   panel** — hiding the panel doesn't fix it.
3. Given this is a Streamlit-internal layout interaction, not a
   single Prism CSS rule, root-causing the actual trigger (which element's
   text is the one collapsing the shrink-to-fit calculation) needs
   dedicated investigation time this run's budget didn't have left.
   **Reverted both attempts rather than ship a fix that only hides the
   symptom** (`display: none`) while leaving the actual "app is unreadable
   on a phone" problem unsolved — shipping that under the label "fixed the
   mobile bug" would repeat the same overclaiming pattern this audit's
   headline finding called out above.

**For the next run that picks this up:** start from
`mobile_content_squish_bug_evidence.png` (reproduce: load any sample
dataset at a 390px viewport, screenshot the Overview tab) and binary-search
which widget's text is the trigger — likely something with a long
unbroken string (a filename, a code snippet, a URL) inside a `stMarkdown`
that lacks a `min-width` guard. A probable fix shape: add
`min-width: 0` overrides are already implicit; more likely a **min-width
floor on `.stVerticalBlock` itself** (e.g. `min-width: min(100%, 280px)`
in a mobile media query) forces the shrink-to-fit calculation away from
the degenerate single-character solution without needing to find the
exact trigger element. This is now a higher-priority backlog item than
Run 2's framing suggested — it affects the *entire* Overview tab on phone
widths, not just the Atlas panel's overlap.
