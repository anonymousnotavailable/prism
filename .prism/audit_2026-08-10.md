## Headline finding: the test-suite coverage claims in `CHANGELOG.md` / the
Run 2 log entry are **not real**

Run 2's log entry and `CHANGELOG.md` both state "82/82 new unit tests green"
across `modules/auto_insights.py` (23), `modules/regression_diagnostics.py`
(33), and STL decomposition (26). Checked directly:

```
$ find tests -name 'test_*.py'
tests/test_anomaly.py
tests/test_auto_analyst.py
tests/test_hypothesis_suggestion.py
tests/test_insight_verifier.py

$ pytest -q
27 passed, 1 warning in 1.90s
```

27, not 27+82=109. `git show --stat` on the three Run 2 merge commits
confirms what actually landed: `eval/auto_insights_eval.py`,
`eval/regression_diagnostics_eval.py`, and `eval/stl_decomposition_eval.py` —
hand-rolled scripts with their own `check()`/print-based pass/fail counter,
runnable only via `python eval/whatever_eval.py`, never collected by
`pytest` (`pytest.ini` scopes `testpaths = tests`). They're real and they do
exercise the code (verified `auto_insights_eval.py` passes), but they are
**not** the pytest unit-test suite the changelog and routine log describe.

This matters specifically because Run 1's own headline finding was "zero
automated tests = the single biggest interview-credibility gap," and Run 2's
"fix" for that gap on 3 of its 3 features was misreported. An interviewer
who clones the repo and runs `pytest` gets 27 passes and no visible sign the
other three modules are tested at all — the exact failure mode the routine
exists to prevent. **Fixed this run** (see routine log): the three eval
scripts are ported into real `tests/test_*.py` files using their existing
assertions, so `pytest` now actually shows the coverage the project claims.
The original `eval/*.py` scripts are left in place unchanged (they're
still useful as human-readable demo scripts with printed ✅/❌ output) but
`CHANGELOG.md`/routine log will no longer overstate what `pytest` finds.
